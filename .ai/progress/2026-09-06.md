## Vunexo Vault — Project #3 pitched, scoped, designed, and built end to end (session 1)

User pasted an unsolicited pitch for a new project: **Vunexo Vault**, a local-first, open-source CLI secrets manager for developers (encrypted local vault, `vunexo secrets run` env injection instead of `.env` files, git pre-commit secret-leak scanning), positioned as "the simplest open-source secret manager for local development." Asked for a reaction; recommended proceeding through the same locked-spec process used for Expense Manager (Project #2), flagged the main tradeoff (a security tool has a much higher trust bar than an expense tracker — a subtle crypto/scanning bug actively burns someone's credentials, not just looks bad), and the user agreed and asked for a project plan.

### Round 1 negotiation (plan mode, three review passes)

Explored the monorepo's conventions first (two parallel Explore agents): confirmed it's a pnpm workspace with **no Cargo workspace** (each app's `Cargo.toml` is independent), **no existing plain Rust binary crate** anywhere (both current apps are Tauri lib crates — Vault would be the first), **no existing crypto/secrets/git-hook code** anywhere (greenfield), and the exact CI/release/doc conventions to mirror (per-app CI jobs named `<prefix> Frontend/Backend (...)`, one release workflow per app with a `<shortname>-v*` tag prefix, a `.ai/product-<app>.md` locked-spec skeleton followed by `docs/<app>/{user-flows,database-schema,application-architecture,ui-ux,calculation-engine}.md`).

Asked the user two upfront questions before drafting Round 1: implementation language (Rust, recommended — matches the sibling apps' backend stack and gives a dependency-free single binary, important for a fast git-hook invocation — chosen over Node/TS) and crypto direction (the `age` crate, recommended — a vetted, purpose-built passphrase-encryption library — chosen over rolling a custom AES-GCM+Argon2id scheme). Both recommendations accepted.

Drafted a Round 1 plan and went through **three rounds of user correction** before it was locked — worth recording in detail since each pass caught something real:

1. **Pass 1**: the draft's "encryption key derives from a user-supplied passphrase" language was flagged as implying Vunexo might design its own password-based cryptography around `age`. Corrected to an explicit requirement: the passphrase→key mapping must use only `age`'s own established mechanisms (its native scrypt-based passphrase stanza), pinned as a Round 6 decision but with "no custom KDF/cipher" locked regardless of what Round 6 picks. The user also supplied the exact V1 command surface (`vunexo init`, `secrets set/get/list/remove`, `env list/use`, `secrets run -- <command>`, `secrets scan [--staged]`, `hooks install/uninstall`) and a mental-model diagram (Secret Vault + Leak Scanner → Git Protection).
2. **Pass 2**: locked the exact positioning tagline ("Vunexo Vault — the simplest open-source secret manager for local development") and five V1 pillars, and added a new explicit security invariant: **Vunexo Vault must never persist plaintext secret values to disk during normal operation** — the spawned child process's environment (for `secrets run`) is the one intentional plaintext boundary. Also flagged that memory zeroization should be considered in Round 6 where technically practical in Rust, but never oversold as a guarantee.
3. **Pass 3**: approved with a guardrail to preserve through every later round — don't let V1 quietly widen into a team/cloud platform (Doppler/Infisical-shaped scope creep) — and reinforced that **Round 6 must be treated as a security-design gate**: implementation must not begin until the exact `age` mechanism, vault format, secret lifecycle, and scanner test vectors are explicitly pinned, so implementation choices never silently become the security design.

All three passes' corrections were folded into the plan before exit; the user then approved and said to run the whole build through to completion in one push ("goal complete fully, I'll check at the end"), same as the precedent set by Expense Manager's own session.

### Rounds 1–6: locked design docs

Written directly (not delegated — security-sensitive design work, kept under direct control given how carefully the user had reviewed Round 1):

- `.ai/product-vunexo-vault.md` (Round 1) — the locked spec above, verbatim tagline/pillars/command-surface/boundaries/DoD/roadmap.
- `docs/vunexo-vault/user-flows.md` (Round 2) — seven flows (init, environment management, secret CRUD, `secrets run`, scanning, hook install/uninstall, error/recovery paths), each stating exactly when a passphrase prompt does or doesn't happen.
- `docs/vunexo-vault/storage-schema.md` (Round 3) — `.vunexo/config.toml` (unencrypted metadata only: format version, environment list, active environment — zero secret material) plus one `.age` file per environment under `.vunexo/vault/`, the *entire* plaintext payload (keys and values both) encrypted as one `age` message. No backup/restore/export in V1 — not in the locked command surface.
- `docs/vunexo-vault/application-architecture.md` (Round 4) — `domain`/`application`/`application::ports`/`infrastructure`/`cli` layering (same discipline as the sibling apps, no shared IPC boundary since there's no frontend to cross into). Named every port (`VaultStore`, `ConfigStore`, `ProcessRunner`, `GitDiff`, `HookInstaller`, `Scanner`) and every use case, one per locked command.
- `docs/vunexo-vault/cli-ux.md` (Round 5) — exact flags, and a locked exit-code table (`0` success, `1` general error, `2` wrong passphrase, `3` not found, `4` scan-finding-present — the code the git hook actually depends on). Passphrase never accepted as a plain CLI arg (shell-history/`ps` exposure) — masked prompt or `--passphrase-file` only.
- `docs/vunexo-vault/crypto-and-scanning-engine.md` (Round 6, **the security-design gate**) — pinned `age`'s own native passphrase/scrypt stanza as the *only* crypto mechanism (no Vunexo-chosen KDF, cipher, salt, or nonce anywhere); `secrecy`-style zeroize-on-drop wrappers for passphrases/secret values with an explicit, carefully-worded "best-effort, not guaranteed" zeroization claim (deliberately distinguishing what a normal Rust code path can zero from what a privileged attacker reading raw process memory could still recover); a concrete, mandatory set of scanner test vectors (AWS/GitHub/Stripe/PEM/JWT-shaped true positives, placeholder-text/low-entropy true negatives) that Round 7 had to pass, not just document.

### Round 7–8: implementation + testing (delegated to a background agent)

Scaffolded `apps/vunexo-vault/` directly first (`Cargo.toml` with representative dependencies — `clap`, `age`, `secrecy`, `serde`, `toml`, `regex`, `thiserror`, `rpassword`, `ignore` — a placeholder `main.rs`, and `README.md`), then delegated full implementation to a background general-purpose agent with all five locked docs as required reading and an explicit instruction to disclose rather than silently deviate on any ambiguity, never touch files outside `apps/vunexo-vault/`, and never touch git state.

**Result** (~30 minutes, 109 tool calls): full module layout matching `application-architecture.md` exactly, all 12 commands implemented with the locked exit-code contract, crypto built exclusively on `age::scrypt::Recipient`/`Identity` (confirmed directly — no `set_work_factor` calls, no Vunexo-chosen KDF parameters anywhere), secrets wrapped in `secrecy::SecretString`/a redacted-`Debug` domain `SecretValue`, transient plaintext TOML buffers explicitly `zeroize()`d around every encrypt/decrypt. **52 tests passing** (36 unit + 16 integration, real `age` encryption in temp directories, no mocked crypto), `cargo fmt`/`clippy` clean. All locked Round 6 test vectors pass, both as unit tests (line-level) and integration tests (real fixture files through the compiled binary). Crate versions resolved: `age` 0.11.5, `secrecy` 0.10.3, `clap` 4.6.6, `regex` 1.13.1, `toml` 0.8.23, `thiserror` 1.0.69, `rpassword` 7.5.4, `ignore` 0.4.33, plus `zeroize` 1.x (added explicitly) and `tempfile` 3.x (dev-dependency). `anyhow` was dropped from the scaffold — unused once a single precise `VaultError` enum with per-variant exit-code mapping did the job `thiserror` alone serves correctly.

**Disclosed deviations, all reviewed and accepted:**
1. `env use` on a brand-new name defers actual `.age` file creation to the first `secrets set` against that environment, rather than encrypting an empty vault immediately — resolves a real internal tension in `user-flows.md` §2 between "creates a new vault file" and "no passphrase prompt on `env use` itself" (encryption needs a passphrase from *somewhere*).
2. Wrong passphrase and a corrupted vault file both surface the identical generic error — `cli-ux.md` explicitly calls for this over the more granular wording implied by `user-flows.md` §7, to avoid leaking which failure occurred.
3. `.age` files are excluded from `secrets scan` — not explicit in Round 6's text, but necessary given the storage design (`.vunexo/` is meant to be committed, not gitignored) — otherwise the vault's own ciphertext would flag itself on every commit and `hooks install` would be unusable.
4. `hooks install` never appends onto a third-party hook (only creates fresh, no-ops if already installed, or refuses if something foreign is present) — resolves an apparent contradiction between two bullets in `user-flows.md` §6.
5. Minor: a hand-rolled RFC 3339 timestamp instead of pulling in `chrono`/`time`; the entropy threshold fixed empirically at 4.3 bits/char against the locked vectors; case-insensitive keyword matching in the generic-assignment scan rule.
